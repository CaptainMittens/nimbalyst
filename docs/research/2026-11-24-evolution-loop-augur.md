# Evolution loop spec: outside-behavior claims

## Question
Five claims in the spec rest on behavior outside the repo: auto-memory loading, worktree memory folders, plugin skills through the Agent SDK, a stats library for the verdict, and the Hermes Atlas rule. Does each one hold?

## Finding

Tier note: Onyx (`onyx-remote`) was unreachable (Cloudflare tunnel error 1033), so it was skipped. Episodic memory and Context7 were not queried; the official Claude Code docs were fetched directly (Tier 4). The Atlas source was read from disk (Tier 1).

### 1. MEMORY.md loading and cap: Suspect-advisory
- Docs: "the first 200 lines or 25KB of `MEMORY.md`, whichever comes first, load at session start" and "everything past the limit is dropped on the next load" (code.claude.com/docs/en/memory, "How it works").
- Agent SDK: auto memory is "Loaded into the system prompt at session start", and `settingSources` does not control it (code.claude.com/docs/en/agent-sdk/claude-code-features, "What settingSources does not control").
- Measured: the live file `~/.claude/projects/-Volumes-josh-external-Projects-Nimbalyst/memory/MEMORY.md` is 37 lines, 6,870 bytes (`wc -l -c`). A 1,400-character section fits today.
- Path: the docs say the memory folder is `~/.claude/projects/<project>/memory/`. They do not say the system prompt states the path. This session's context does show the full path beside the loaded MEMORY.md text (observed), but a Nimbalyst SDK session was not observed. Treat as unverified for SDK sessions.
- Risk: the spec appends the section at the END when markers are missing. memory-spike also appends its own section at the end. If the file passes 200 lines or 25KB, the lessons are cut off with no error to the reader.
- Spec fix: insert missing markers near the TOP (after the first heading or index), and stop with a clear failure when the skill cannot see a memory folder path.

### 2. Worktree memory folder: Verified (shared), with a gap
- Docs: "The `<project>` path is derived from the git repository, so all worktrees and subdirectories within the same repo share one auto memory directory. Outside a git repo, the project root is used instead."
- Local gap: `/Volumes/josh_external/Projects/Nimbalyst` is not a git repo (its CLAUDE.md says so), so sessions there use `-Volumes-josh-external-Projects-Nimbalyst`. Sessions in the `nimbalyst` clone and its worktrees (git repo) use a key derived from the clone. PREDICTION: those are two different folders. Disk: no `memory/` folder exists for the clone's key.
- Disk noise: worktree-named memory folders exist (rpg-system, Phoenix, Nimbalyst-Plugins). Their MEMORY.md text starts with "Auto-generated by `memory-spike learn`", so memory-spike wrote them. They do not show how Claude Code keys the folder.
- Spec fix: say lessons reach only sessions that share the folder the skill wrote to (the parent-folder sessions versus clone sessions may differ).

### 3. Plugin skills through `options.plugins`: Sound
- Docs: `{type:'local', path}` is the only accepted type; skills appear as `plugin-name:skill-name` in the init message; path must be the plugin root; "If a plugin path doesn't exist, the SDK skips that plugin" (agent-sdk/plugins).
- Frontmatter: "All fields are optional. Only `description` is recommended." `name` defaults to the directory name (code.claude.com/docs/en/skills). The spec's `name` plus `description` is stricter than needed and safe.
- Spec fix (optional): a test should read the init message `plugins` list, because a bad path fails silently.

### 4. Stats test: Suspect-advisory
- Spec D8 says `rg` over `packages/*/package.json package.json` found no stats library. That glob is one level too shallow. `rg` over all package.json found `"mathjs": "^15.2.0"` at `packages/extensions/calc-sheets/package.json:18`. No `simple-statistics`, `jstat`, `d3-array` or `@stdlib` hit anywhere.
- mathjs 15.2.0 (`node_modules/mathjs/types/index.d.ts`) has `erf`, mean, std and similar, but no z-test or Fisher function.
- Power at the spec's minimums (python3, Fisher exact two-sided): 5/20 before versus 2/20 after gives p = 0.407. 10/40 versus 3/40 gives p = 0.066. The 0.5-ratio rule would call the first case `effective` on noise.
- Options, not a decision: (a) keep native arithmetic and call it a screening rule, as Atlas does; (b) raise the minimums; (c) a two-proportion z-test is about six lines on mathjs `erf` (needs mathjs added to the electron package: owner's yes); (d) npm `fishers-exact-test` 1.0.5 is weak (4 years old, depends on big.js, about 5 weekly downloads per npm.io).

### 5. Hermes Atlas rule: Suspect-advisory (wording)
Read from `lessons.py` (plugin v0.13.0):
- `MIN_TOTAL = 3` (line 23), `BASELINE_DAYS = 14` (line 24), `AFTER_WINDOW_DAYS = 14` (line 635). Verdicts `effective` (`after <= 0.5 * before`, line 794), `ineffective` (`failures_after >= 3 and after >= 0.9 * before`, line 796), else `inconclusive`. The spec's cite `lessons.py:794-796` is correct.
- Differences from the Prior Art wording: Atlas needs 3+ hits in 2+ sessions OR on 2+ days (lines 420, 441), not 2+ days only. Atlas judges at 5 days or 20 calls (`EVALUATE_AFTER_DAYS=5`, `EVALUATE_AFTER_CALLS=20`, line 789), not after the full 14-day after window. Atlas retires an `ineffective` lesson only in auto mode, after 14 active days, and not when the owner kept it (about line 801).
- Spec fix: Prior Art says "Atlas rules adopted" for 3+ hits on 2+ days. Change to "Atlas's 3+ hits in 2+ sessions or days; the spec uses days only and judges at day 15."
